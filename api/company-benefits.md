# 企业福利：合法公开来源收录

本次改造仅支持企业合法公开信息，不开放员工内部材料投稿或企业授权材料上传。界面统一使用“平台审核收录”，不得将平台审核描述成企业确认或政府认证。

## 收录边界

- 允许投稿企业官网、企业官方招聘公告等公开来源与对应的事实摘要。审核员逐项核验发布主体、公开渠道、内容一致性、适用岗位、城市和日期。
- 不以员工群、内网、匿名泄漏、个人网盘或员工持有的内部文件作为公开依据。公网可打开的链接不自动证明来源合法，人工核验必不可少。
- 每项福利独立绑定来源，不得依据餐补公告推断内部奖金、职级薪酬矩阵等其他待遇。
- 不收集在职证明、工资明细、劳动合同、内部制度截图或录屏；不得通过内部原件整理、转述受保护内容后公开。
- 企业授权模式需另行完成企业身份、授权人权限、范围、渠道、期限、撤销及个人信息等流程后才能开放。

这是产品收录政策，不是认定所有内部福利都属于商业秘密。法律上的商业秘密须结合非公知性、商业价值和保密措施具体判断。

## 手机端

企业名称搜索、城市筛选、分页及我的提交保留。每项非空待遇都填写公开来源链接和发布主体，可填来源发布日期。用户确认内容来自合法企业公开渠道，平台另行审查，用户确认不替代平台核验。

删除文件选择与上传流程；重新提交旧记录只提交公开来源，不复用历史附件。公开详情显示对应来源、发布主体、来源发布日期及来源核验日期。新版客户端连接旧服务时，对缺少逐项来源或核验时间的列表和详情不展示。

公开详情提供“信息纠错 / 侵权投诉”，复用 `POST /api/v1/reports`，对象为 `COMPANY_BENEFIT`。描述限200字，说明具体条目、权利关系和可核验线索，不复制秘密原文或个人资料。返回受理编号，不宣称提交后自动下架或已认定侵权。

## 请求和审核

`content.sources` 按福利类别与 `content.benefits` 一一对应：

```json
{
  "benefits": { "leave": "公开公告中适用于该岗位的休假安排摘要" },
  "sources": {
    "leave": {
      "url": "https://company.example.com/careers",
      "publisher": "企业公开发布主体",
      "published_on": "2026-10-10"
    }
  }
}
```

- URL 只允许 HTTP/HTTPS 绝对地址，无嵌入凭据；拒绝 IP、单标签、localhost、内网后缀等不适合作为公开依据的链接。服务端不自动抓取用户 URL。
- 发布主体2–120字；可选发布日期为有效 YYYY-MM-DD，不能晚于今天。格式校验只能筛除无效输入，不能替代人工核实。
- 原 `employment_file_ids` 和 `evidence_file_ids` 兼容字段只能为空；带内部附件的 POST/PATCH 返回 `PUBLIC_SOURCES_ONLY`，缺公开来源不能提交。
- `EMPLOYMENT_PROOF` / `BENEFIT_EVIDENCE` 上传申请和完成接口均拒绝新请求。旧上传授权的完成动作也拒绝。已经签发的存储 token 可能在到期前仍能上传对象，服务端拒绝确认/引用；上线时应使旧 token 到期或按存储能力撤销，并检查遗留对象。
- 管理员直接新增、修改公开记录及投稿 APPROVED 都要求顶层 `sources_verified: true` 和10–1000字 `source_review_note`，记录核验企业身份、逐项来源与适用范围。任何内容修改或重开页面均重新确认，不沿用旧确认。
- 发布必须逐项具备公开来源；来源缺失的旧投稿只能退回或拒绝，不能把审核内部材料作为来源核验。非公开存储与拒绝/退回不依赖来源完整性。
- 公开 `official_note` 必须为空，避免无来源自由文本夹带额外待遇；岗位/日期使用结构化字段，核验说明留在管理端。
- 原始附件的管理员日常签名链接停止签发，历史文件只返回受权限保护的元数据。公开接口不返回附件、提交人、核验人或内审说明。

## 数据迁移与历史记录

新增 `042_company_benefit_public_sources.sql`，由主 API 迁移：

- 企业库保存逐项 `sources_jsonb`、`source_reviewed_at`、`source_reviewed_by`、`source_review_note`。
- 状态为 `SOURCE_REVIEW / PUBLISHED / ARCHIVED`，新记录默认待来源核验。
- 历史已公开记录进入 `SOURCE_REVIEW` 并增加 revision；不删除旧记录、附件或原始提交，不将旧“已审核”迁成来源已核验。
- 数据库 CHECK 阻止来源缺失、无核验人/时间/说明或有无来源公开备注的记录变成 PUBLISHED；App 列表和详情仍显式检查公开状态与来源核验时间。
- 原证明数组允许为空，保留旧数据的数量上限以兼容历史。

历史资料应保持访问隔离，并依据处理目的、争议留证需要及个人信息要求确定保留/删除规则。此版本不自动销毁历史证据，也未虚构已完成存储对象清理。对疑涉密旧资料不能继续用于日常收录、训练或导出。

## 纠错与投诉处置

举报中心显示投诉描述供授权人员判断。只有企业福利的 RESOLVED 处理可明确选择 `content_action: SUSPEND`，默认 NONE，不因任何投诉自动暂停。SUSPEND 在同一事务中将记录改为 SOURCE_REVIEW、清核验时间/核验人、增加 revision 并留下审计；其他对象或 DISMISSED 不能使用该动作。恢复必须重新核验来源后在福利后台发布，举报分类操作不能直接恢复。

运营应根据权利人身份、初步证据和服务性质及时采取必要措施，转送通知、受理申辩并记录复核；新入口和暂停操作不替代上述人工处理。内部审核意见、通知和日志避免重复披露秘密正文。

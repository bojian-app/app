# 博简 Issue 驱动开发

适用仓库：`fahnzjan/bojian-mobile`。操作前核对当前仓库及远程地址，避免更新其他项目的 Issue。用户已明确要求本项目遵循该流程，并授权与任务对应的 Issue 创建、进度更新、结果说明与关闭；无需逐次询问。提交、推送、合并和发布仍以当前会话已有授权为准，不能由本技能额外推定。

## 开发前

1. 先查看工作区和相关开放 Issue。用户给出 Issue 时先读取；同一任务已有匹配 Issue 时继续使用，不重复建单。无匹配项则在实际修改文件前创建 Issue，包含问题或需求、准备变更的范围，以及可验证的验收标准。只读排查可先进行，以便写清问题。
2. 用用户沟通语言编写标题和正文，简洁、具体。向用户提供 Issue 链接后继续开发，不额外等待确认。独立问题分别建单；同一目标的后续澄清或修正更新原 Issue。
3. 优先使用可用的 GitHub 工具或已登录的 `gh`。若 CLI 不可用，可使用已授权的 GitHub API；不得输出或提交凭证。网络或权限暂不可用时说明实际失败原因并准备 Issue 草稿，解决访问问题后先成功建单再实施，除非用户明确豁免。

Issue 正文可按以下内容组织：

```markdown
问题或需求：描述触发条件、实际表现和期望结果。

准备变更：
- 说明拟修改的行为及相关范围。

验收标准：
- 说明用户可观察的结果和必要的回归检查。
```

## 开发与验证

- 围绕 Issue 的范围实施；范围或验收标准变化时同步更新 Issue。保留与当前任务无关的工作区改动。
- 按变更风险进行必要验证，记录实际结果及未验证的限制；不为纯文字或低影响变更机械增加测试。
- 继续已有未完成工作时读取其 Issue 和提交记录；若开发早于本流程且没有 Issue，补建并如实注明“补建”，不能宣称事前已建。

## 提交前代码审查

实现和必要验证完成后，仅使用以下三个 Flutter 技能作为技术审查依据，按最终改动选择适用内容：

- [flutter-apply-architecture-best-practices](../flutter-apply-architecture-best-practices/SKILL.md)：检查架构分层、状态与数据职责。
- [flutter-add-widget-test](../flutter-add-widget-test/SKILL.md)：检查组件行为及相关测试。
- [flutter-fix-layout-issues](../flutter-fix-layout-issues/SKILL.md)：检查布局约束、溢出及显示问题。

审查最终拟提交内容；不涉及的技能范围注明不适用，不为套用示例扩大改动。纯文档或配置变更检查内容一致性、引用和配置有效性，无需强行增加 Widget 测试或运行界面。测试通过不能替代代码审查。

修复审查发现的问题并复查；审查后新增或修改的内容也必须复查。记录审查范围、问题处理、验证及明确结论。审查通过前不得提交或推送；通过后直接放行已有授权的提交和推送，无需额外确认或另设审查技能。自审须如实注明，不能声称完成独立审查。

## 提交与推送

在已获得提交／推送授权时，提交记录采用“一句话概述，空行，具体变更小点”，并关联 Issue。只有开发授权时，完成实现和验证，保留 Issue 开放并报告待提交／待推送状态。

```text
修复微信导入简历保存后未回到我的简历的问题

- 保存成功后切换到简历标签并关闭导入相关页面
- 补充保存跳转的回归验证

关联：#123
验证：说明实际执行的检查和结果
```

- 将提交范围限定为已完成并能说明的变更；多个相关 Issue 分别列出。不要把其他任务的未完成文件一并提交。
- 通过 `#编号` 或跨仓库完整链接关联 Issue。使用普通关联引用，在验证完成后明确关闭，不依赖推送或合并触发提前自动关闭。
- 推送到当前任务约定的远程与分支，检查命令成功且相应远程分支包含目标提交。失败时保留 Issue 开放并报告原因。

## 关闭 Issue

仅在验收标准满足、必要验证和代码审查通过、相关提交成功推送后关闭；若任务要求合并或发布也作为验收条件，先完成该条件。

先在 Issue 中补充完成说明：具体变更、提交链接、审查结论、验证结果和必要限制，再标记为已完成。若用户已要求关闭，可用支持附带完成说明的关闭操作一次完成。

取消、实现未完成、测试未通过或未推送时不要标记为已完成。用户明确取消并要求关闭时可以关闭，但说明取消原因并使用“未计划／不再处理”的关闭原因。

最终回复提供 Issue 与提交链接、推送及关闭状态、关键验证结果。不能将“本地已完成”写成“已推送／已关闭”。
